# 后端质量门禁

本文定义后端修改达到交付条件的执行要求。[AI Java 开发规范](ai-java-development.md)定义编写要求；业务边界、JDK、构建命令和现有测试能力见[后端工程规范](engineering.md)。

开发者或 AI 必须实际执行适用门禁并提供结果；文档中的要求不代表现有 Maven 命令已自动执行全部检查。

## 适用范围

- 后端生产代码或测试代码修改，执行下列 4 次规范检查、3 次代码 Review，再完成适用的测试验收。
- 仅配置、依赖或 SQL 修改，也执行该流程，检查对应运行行为和调用链。
- 仅修改文档时，检查内容一致性、事实、链接、Markdown 格式与 diff；不触发代码审查轮次、应用测试或覆盖率采集。
- 检查本次改动及受影响的调用链，保留已有未提交工作。全仓审查只在任务明确要求时执行。

## 检查与修复顺序

**编写完成 → 规范检查 1 → Review 1 → 规范检查 2 → Review 2 → 规范检查 3 → Review 3 → 规范检查 4 → 测试验收 → 交付汇报**

| 阶段 | 检查重点 |
|------|----------|
| 规范检查 1 | 对照 AI Java 开发规范检查改动及调用方，重点核对分层、输入边界、异常原因链、敏感信息、SQL、事务、写入结果和设计复杂度 |
| Review 1 | 正确性与健壮性：需求、正常流程、边界、状态变化、依赖故障，以及错误成功响应、吞异常或部分写入 |
| 规范检查 2 | 核对第一轮修复后的完整改动，确认修复仍符合规范且没有扩大任务范围 |
| Review 2 | 集成与修改影响：接口、配置、数据库映射、权限和事务是否一致，前一轮修复是否影响其他调用方 |
| 规范检查 3 | 核对第二轮修复后的完整改动，检查异常、数据一致性和敏感信息要求是否仍成立 |
| Review 3 | 可维护性与最终差异：职责、命名、可读性、复用、无用分支、过度设计，以及测试是否证明关键行为 |
| 规范检查 4 | 对照规范核对最终版本，确认前三轮问题已解决，代码与事实文档、测试一致 |

每轮必须实际检查对应内容。有依据的问题在任务范围内直接修复，并运行受影响的测试；没有问题就记录无发现，不为凑数量新增问题或重构。规范检查核对规则，Review 沿真实调用链判断行为，不能用重复阅读或同一份结论代替全部阶段。

规范检查 4 或最终测试中再次修改代码时，对修改部分补做 Review、规范检查及受影响的测试，确认这些修改不会破坏已验证的行为。无需重跑未受影响的所有阶段；代码、配置或依赖变化后，最终构建仍须对应最终版本。

## 测试验收

在实施和 Review 中列出本次改动的需求、关键业务分支、正常流程、边界、状态变化及已识别失败场景，明确预期结果和对应验证。对照下表确定必需测试，不适用时记录具体原因。

| 类型 | 触发条件 | 通过标准 |
|------|----------|----------|
| 单元测试 | 业务规则、算法或异常处理修改 | 相关正常、边界和失败行为断言通过；缺陷修复有能复现问题的回归验证 |
| 集成测试 | 数据库、Redis、鉴权、事务、序列化或相关配置修改 | 覆盖实际受影响的框架与存储边界；Mock 不能作为该边界真实可用的证据 |
| 冒烟测试 | 生产代码、运行配置、依赖或 SQL 修改后的最终交付 | 应用在独立环境启动成功，受影响的关键接口及主要流程实际跑通；上下文测试或 MockMvc 不能替代真实启动和 HTTP 检查 |
| 回归测试 | 所有代码修改的最终交付 | 执行现有测试，并覆盖受影响的既有功能和已修复缺陷；必需测试无失败、无未处理错误 |
| 并发测试 | 认证、事务、原子操作、唯一约束、锁或共享状态修改 | 对同一资源制造实际重叠请求或操作，验证业务不变量、结果分布和最终数据；串行重复请求不能替代并发验证 |
| 压力测试 | 性能或容量相关改动、重要版本交付 | 事先确定请求规模、持续时间、响应时间和错误率标准；实测指标满足标准，资源使用及负载结束后的恢复符合预期 |

### 当前认证业务的并发重点

仅在对应改动触发时执行相关场景；具体期望以现有[接口文档](api.md)与业务方案为准。

- 同一个验证码同时消费，最多一个请求成功。
- 同一验证码场景与联系方式并发发送，60 秒发送锁生效；每日计数无丢失更新，允许发送次数不超过既定上限。
- 同一联系方式并发注册，最多创建一个账号，唯一键冲突按业务契约响应。
- 并发修改渠道配置，手机号和邮箱总开关不能同时关闭。
- 普通用户密码修改提交后，使用旧密码版本的 Refresh Token 续期失败；普通用户已签发 Access Token 的剩余有效期以及与改密重叠的 Refresh，遵循既定方案，不增加跨 PostgreSQL/Redis 强一致要求。
- 系统用户认证版本或状态更新提交后，新发起的受保护请求按数据库最新状态校验；已完成认证的并发在途请求允许完成。密码重置和状态变更后的系统用户旧 Access Token 与 Refresh Token 均失效，重新启用不会恢复旧版本。

### 压力测试的执行要求

测试前写明目标接口、操作比例、并发数或请求速率、预热与持续时间、测试数据，以及响应时间和错误率阈值。需要不同负载阶段时明确各阶段规模；超载测试区分预期拒绝与系统异常。指标依据当前需求或已确认的容量目标确定，不临时编造阈值制造通过。

记录实际吞吐量、P95/P99 响应时间、错误率、CPU、内存及受影响的数据库连接或 Redis 指标。负载结束后验证主要流程恢复正常。只在独立测试环境使用可丢弃数据，不向生产或共享业务环境施压；不在报告中记录凭据、完整 Token 或完整敏感联系方式。

### 覆盖率与测试结果

- 本次明确列出的需求、关键分支和已识别失败场景，必须 **100% 有对应验证且符合预期**。这是场景清单的验收要求，不代表所有未知场景均已覆盖。
- 使用支持当前 JDK 的工具采集行覆盖率和分支覆盖率，报告统计范围、排除项及未覆盖的关键代码。不能为达标排除业务代码或添加无有效断言的测试。
- 不统一要求代码行覆盖率或分支覆盖率达到 100%；优先补齐关键业务与失败路径，低覆盖率需要分析实际遗漏。
- 最终版本要求执行的测试必须全部通过。标记“跳过”“未执行”“未采集”的项目不能计为通过；不适用项目说明原因。
- 代码或测试修改须有覆盖率采集结果；仅配置、依赖或 SQL 修改时按受影响的代码路径确定是否需要重新采集。必需采集缺失时，门禁未通过。

## 通过标准

只有以下适用项全部满足，才能报告“通过质量门禁”：

1. 完成要求的规范检查和 Review，已确认的问题均已修复并验证；没有遗留影响正确性、安全性、健壮性或维护性的已确认问题。
2. 场景清单中的必需验证全部通过，覆盖率要求按上节满足；必需的集成、冒烟、并发或压力测试没有缺失、失败或以跳过替代执行。
3. 在 `backend` 目录使用工程规范指定的 JDK 25 执行 `.\mvnw.cmd verify` 成功。该命令证明测试和打包结果，其他验收项仍须有对应执行证据。
4. 接口、配置、数据库或运行方式改变时，相关事实文档已同步；数据库结构变更新增不可变的 Flyway 版本迁移，CI 在空的真实 PostgreSQL 17 测试库验证迁移。
5. 检查最终 diff 与 Git 状态，`git diff --check` 通过；改动范围清楚，没有覆盖已有工作或混入临时数据、凭据及生成物。

纯文档修改只适用范围、内容、链接、格式和 diff 检查，其他项标记不适用。环境或工具阻塞不改变必需项的通过标准；可以汇报已完成的修改，但门禁状态必须写为“未通过”，并指出缺失证据。

## 交付记录

默认在最终汇报中记录以下内容，不为每一轮额外创建重复报告文件：

- 改动范围、解决的问题和最终门禁状态。
- 4 次规范检查与 3 次 Review 的发现及处理结果；没有发现时如实记录。
- 各类适用测试的执行命令或脚本、结果和报告位置，区分通过、失败、跳过、未执行与不适用。
- 场景清单覆盖情况、行覆盖率和分支覆盖率；适用压力测试的目标、阈值和实测指标。
- 未解决问题、缺失验证及实际交付状态；提交、推送或发布仍遵循用户在当前任务中的授权。
