# AI Java 开发规范

> 基于《阿里巴巴 Java 开发手册（黄山版）》1.7.1 精简并改写，供 AI 编码代理直接执行。
> 官方来源：[alibaba/p3c](https://github.com/alibaba/p3c/blob/master/Java%E5%BC%80%E5%8F%91%E6%89%8B%E5%86%8C(%E9%BB%84%E5%B1%B1%E7%89%88).pdf)
> 本文件不是原手册全文。它保留适用于现代 Java 项目的规则，并以当前项目约束为准。

本文件定义代码、测试和文档的编写要求。后端检查顺序、测试触发条件与交付标准统一见[后端质量门禁](quality-gates.md)。

## 1. 执行方式

### 1.1 规则等级

- **【必须】**：默认不可违反。违反会造成正确性、安全性、可维护性或交付问题。
- **【应当】**：默认执行。只有当前需求、项目约定或现有架构给出明确理由时才偏离。
- **【可以】**：按当前需求选择。没有实际收益时不要引入。

不要把“应当”和“可以”扩展成额外任务。只修改完成当前需求所必需的内容。

### 1.2 冲突优先级

发生冲突时，按以下顺序执行：

1. 用户在当前任务中的明确要求。
2. 项目内的业务文档、接口文档、构建配置和数据库定义。
3. 已存在并仍被调用的代码契约与测试。
4. 本规范。

发现文档、代码和测试互相矛盾时，先查明当前真实行为和调用方，再修改。不要自行选择最方便的一方。

### 1.3 修改原则

- 【必须】先阅读目标代码、直接调用方、数据结构、配置和相关测试，再实施修改。
- 【必须】实现满足当前需求的最小正确方案，不为假想需求添加兼容层、扩展点、框架或备用流程。
- 【必须】保持修改范围集中。不要顺手重构无关代码、统一全仓库风格或更换技术栈。
- 【必须】保留用户已有的未提交修改。不能通过重置、覆盖或批量格式化清除无关工作。
- 【必须】新增分支、抽象、缓存、锁、重试或依赖时，必须存在当前调用方或可达的失败场景。
- 【必须】输入的必填、格式、长度等约束在各个不可信入口完成校验；内部代码依赖已经建立的输入契约，不逐层重复同一校验或补默认值。
- 【必须】账号状态、资源归属、业务权限和数据库约束按各自职责验证，不能作为“重复校验”删除。
- 【必须】只捕获能够处理、恢复或转换的异常。不能吞掉异常，也不能把失败伪装成成功、空集合或默认对象。
- 【应当】优先复用项目已有组件和写法。只有复用会造成明显错误或复杂性时才引入新实现。
- 【应当】先使用 JDK、Spring 和现有依赖提供的能力，再考虑增加依赖或自建工具。
- 【应当】注释说明“为什么”，代码表达“做什么”。不要用注释复述代码。

### 1.4 当前项目的固定边界

- 【必须】业务/API 不为未发布的旧接口保留兼容层；已有数据库卷的 schema 接管按 `docs/database-migrations.md` 的显式 baseline 流程处理。
- 【必须】允许为正确设计直接调整接口、模型和表结构，并同步修改当前调用方、文档和测试。
- 【必须】数据库结构与初始数据以 `src/main/resources/db/migration/V*.sql` 的 Flyway 版本迁移为准；已发布迁移不可编辑，只能追加新版本。`web_project.sql` 是旧版手动初始化快照，不再作为新安装或 CI 的 schema 来源。
- 【必须】不要为旧字段、旧表、旧 Token、旧响应结构或未上线版本保留双写、回退和兼容代码。
- 【必须】后端技术版本以 `pom.xml` 为准；当前项目使用 JDK 25、Spring Boot 4 和 MyBatis Spring Boot Starter 4.x。MyBatis 核心版本以实际解析的依赖为准，不与 Starter 版本混用。
- 【必须】具体业务边界以 `docs/engineering.md` 和 `docs/api.md` 为准。

## 2. 命名与代码组织

### 2.1 命名

- 【必须】包名全部小写，按业务域和职责组织，使用有明确含义的英文单词。
- 【必须】类名使用 `UpperCamelCase`；方法、参数、字段和局部变量使用 `lowerCamelCase`。
- 【必须】常量使用 `UPPER_SNAKE_CASE`。
- 【必须】布尔变量使用肯定、可判断的名称，如 `enabled`、`active`、`expired`；Java 属性不要使用 `is` 前缀。
- 【必须】异常类以 `Exception` 结尾；测试类以被测对象或行为命名，并以 `Test` 结尾。
- 【必须】名称表达业务含义，禁止拼音、中文变量名、无意义缩写和 `data1`、`temp2`、`obj` 等占位名称。
- 【必须】同一作用域以及有继承关系的类中，不使用容易混淆的同名变量。
- 【应当】名称优先完整清楚。只有项目通用缩写，如 `DTO`、`VO`、`URL`、`JWT`，才直接使用缩写。
- 【应当】沿用当前项目的领域词汇和后缀，不擅自把 `Entity`、`DTO`、`VO`、`Mapper` 改成另一套命名体系。

### 2.2 类和包职责

- 【必须】按业务域组织代码，并保持 Controller、Service、Mapper、DTO、VO、Entity 的现有边界。
- 【必须】一个类只承担一个清楚的职责。不要创建混合数据库访问、业务逻辑和 HTTP 处理的工具类。
- 【必须】公共代码只有在存在两个以上真实调用方且语义一致时才抽取。
- 【应当】优先使用组合。继承只用于稳定的“是一个”关系或框架要求。
- 【应当】接口服务于真实替换点或跨层契约。单一实现且没有替换需求时，不为形式统一额外创建接口。
- 【应当】不可变的数据载体优先使用 `record`；框架要求可变对象或对象具有生命周期时使用普通类。

## 3. 格式与可读性

- 【必须】默认编写清晰、直接、便于修改和排障的生产代码，命名与结构应让调用方看清输入、业务流程、失败处理和结果。
- 【应当】按业务步骤组织逻辑，必要时使用有明确含义的中间变量。循环、Stream、三元表达式和方法拆分以是否更清楚为判断依据，不追求技巧或最少行数。
- 【必须】注释准确说明业务约束、设计原因和容易误用的地方，并随实现变化更新；不逐行复述赋值、getter 等明显操作。
- 【可以】用户有学习需求时提供教学式解释，详细教程放在独立文档或讲解中；教学式注释不是所有生产代码的硬性要求。
- 【必须】使用 4 个空格缩进，不使用 Tab。
- 【必须】源码使用 UTF-8 和 LF 换行符。
- 【必须】`if`、`for`、`while`、`switch` 等关键字与括号之间保留一个空格。
- 【必须】二元和三元运算符两侧保留一个空格；逗号后保留一个空格。
- 【必须】`if`、`else`、`for`、`while` 和 `do` 的代码块始终使用大括号。
- 【必须】单行注释的 `//` 后保留一个空格。
- 【应当】单行不超过 120 个字符。长字符串、链式调用和参数列表按语义换行。
- 【应当】方法保持单一目标。方法过长或包含多个独立阶段时，按业务步骤拆分；不要只为满足行数创建无意义小方法。
- 【应当】使用提前返回减少嵌套。正常主流程保持连续、清楚。
- 【应当】不同逻辑段之间保留一个空行，不使用多列空格对齐变量或赋值号。
- 【必须】只格式化本次修改涉及的代码，避免制造无关 diff。

## 4. Java 语言规则

### 4.1 对象与类型

- 【必须】覆盖父类或接口方法时使用 `@Override`。
- 【必须】通过类名访问静态成员，不通过对象引用访问。
- 【必须】包装类型使用 `equals` 比较值，不使用 `==`。
- 【必须】可能为空的对象比较使用 `Objects.equals(a, b)`，或由确定非空的一方调用 `equals`。
- 【必须】`BigDecimal` 比较数值使用 `compareTo`；不要用 `equals` 判断数值相等。
- 【必须】创建 `BigDecimal` 时使用字符串构造或 `BigDecimal.valueOf`，不要使用 `new BigDecimal(double)`。
- 【必须】金额使用最小货币单位的整数，或使用明确精度和舍入规则的 `BigDecimal`。不要使用 `float` 或 `double`。
- 【必须】数据库字段类型与 Java Entity 字段类型保持可验证的一致关系。
- 【必须】泛型必须明确，不使用原始类型，不用 `Object` 规避类型设计。
- 【应当】局部变量在值不再变化时使用 `final`，但不要机械地给所有变量添加 `final`。
- 【应当】只使用完成当前逻辑需要的可见性，优先 `private`。

### 4.2 DTO、VO 与 Entity

- 【必须】结构化业务输入使用 DTO，结构化业务输出使用 VO；不能直接把 Entity 暴露为接口请求或响应模型。路径 ID、简单查询参数和无请求体或无返回数据的操作，不为形式统一额外创建包装类。
- 【必须】DTO 只承载输入与边界校验，不包含数据库访问或业务流程。
- 【必须】VO 只表达对外契约，不包含密码哈希、密钥、内部状态或无关字段。
- 【必须】Entity 与数据库列清楚映射。数据库 `is_xxx` 字段映射到 Java 的 `xxx` 布尔属性。
- 【应当】不可变 DTO/VO 使用 `record` 并在组件上声明校验注解。
- 【应当】避免 Lombok `@Data` 扩大 Entity 的 `equals`、`hashCode` 和 `toString` 行为；只使用所需注解。
- 【必须】`toString` 不能输出密码、Token、验证码、密钥或完整敏感联系方式。

### 4.3 空值与 Optional

- 【必须】公开边界清楚定义必填、可空和默认值，不能让 `null` 的含义依赖猜测。
- 【必须】集合返回值使用空集合表示“没有元素”，不返回 `null`。
- 【应当】`Optional` 用于可能缺失的返回值；不要把它用于 Entity 字段、DTO 字段或普通方法参数。
- 【应当】不要使用层层 `Optional` 包装替代清楚的分支和业务错误。

### 4.4 日期与时间

- 【必须】新代码使用 `java.time`，不使用 `java.sql.Date`、`Time`、`Timestamp` 表达业务时间。
- 【必须】日期格式中的自然年使用 `uuuu` 或 `yyyy`，不能误用周所属年 `YYYY`；月份使用 `MM`，分钟使用 `mm`，24 小时制使用 `HH`。
- 【必须】不能写死一年 365 天、一天固定毫秒数等会被闰年或时区破坏的计算。
- 【必须】跨时区的时间点使用 `Instant` 或带时区类型；本地业务日期使用 `LocalDate` 等匹配语义的类型。
- 【应当】时间由系统边界统一获取；只有测试或业务确实需要控制时间时才引入 `Clock`。

## 5. 集合与 Stream

- 【必须】判断集合为空使用 `isEmpty()`，需要同时处理 `null` 时在边界完成。
- 【必须】实现 `equals` 时同步实现满足契约的 `hashCode`。
- 【必须】作为 `Map` 键或 `Set` 元素的对象，在容器存活期间不能改变参与 `equals` 或 `hashCode` 的字段。
- 【必须】`Collectors.toMap` 必须处理重复键；可能出现空 value 时不能直接使用不接受空值的收集方式。
- 【必须】不要把 `subList` 强制转换为 `ArrayList`，也不要在结构性修改父集合后继续使用旧 `subList`。
- 【必须】遍历集合时不直接调用集合的 `add` 或 `remove`。删除使用 `Iterator.remove`、`removeIf` 或生成新集合。
- 【必须】不要修改 `List.of`、`Set.of`、`Map.of`、`Collections.emptyList` 等不可变集合。
- 【必须】数组转集合时清楚 `Arrays.asList` 是固定长度视图。
- 【应当】已知容量时为 `ArrayList`、`HashMap` 等设置合理初始容量，不做脱离数据规模的预分配。
- 【应当】需要键和值时遍历 `entrySet`，不要先遍历 `keySet` 再重复查值。
- 【应当】简单循环比复杂 Stream 更清楚时使用循环。不要为链式写法牺牲异常处理和可读性。
- 【必须】没有性能证据和线程安全分析时，不使用 `parallelStream`。

## 6. 控制流与方法设计

- 【必须】`switch` 的每个分支必须明确终止、返回或使用无歧义的箭头语法。
- 【必须】对可能为空的 `String` 执行 `switch` 前先处理空值。
- 【必须】条件表达式不执行赋值、远程调用、数据库写入等有副作用的复杂操作。
- 【必须】三元表达式两侧类型应一致，避免自动拆箱造成空指针异常。
- 【应当】复杂条件提取成有业务含义的布尔变量或方法。
- 【应当】异常分支优先提前返回或抛出业务异常，避免连续多层 `if-else`。
- 【应当】循环外可稳定计算的值移到循环外，但不要为微小优化破坏可读性。
- 【必须】批量接口必须限制数量、分页大小和输入范围。

## 7. 并发与资源管理

- 【必须】不能在业务代码中直接创建匿名线程。并发任务使用项目管理的执行器。
- 【必须】使用 `ThreadPoolExecutor` 管理平台线程时，明确线程名称、核心线程数、最大线程数、队列容量、拒绝策略和关闭方式。
- 【必须】普通平台线程池不使用 `Executors.newFixedThreadPool` 等隐藏无界队列或线程数量的快捷工厂；优先复用项目中已明确资源上限的执行器。
- 【必须】使用虚拟线程执行器时明确其生命周期，并按实际下游资源容量限制任务并发；不要把虚拟线程池化或套用核心线程数、最大线程数等平台线程池配置。
- 【必须】捕获 `InterruptedException` 后，要么继续抛出，要么恢复中断标记；不能静默忽略。
- 【必须】锁按固定顺序获取，并在 `finally` 中释放。只有成功获取锁后才能解锁。
- 【必须】`ThreadLocal` 使用后在 `finally` 中调用 `remove`，尤其在线程池环境中。
- 【必须】并发更新同一资源时，使用数据库约束、乐观锁或必要的互斥机制保证正确性；不要只依赖“先查后改”。
- 【必须】单例中的共享可变状态必须线程安全。
- 【应当】优先减少共享状态。没有真实并发需求时不要引入锁、异步队列或分布式协调。
- 【应当】远程调用、阻塞 I/O 和慢任务不要占用不匹配的公共线程池。

## 8. 异常、错误码与日志

### 8.1 异常处理

- 【必须】异常用于异常情况，不用于普通流程控制。
- 【必须】业务可预期失败使用项目统一的业务异常和错误码；编程错误和未知系统错误不能伪装成业务成功。
- 【必须】捕获异常时保留原因链。重新抛出时把原异常作为 `cause`。
- 【必须】不能捕获 `Throwable`。除应用边界外，不做无差别 `catch (Exception)`。
- 【必须】事务内捕获异常后不能在数据部分写入的情况下返回成功。
- 【必须】面向客户端的错误响应不能包含堆栈、SQL、表结构、文件路径、密钥或内部实现细节。
- 【应当】在最了解业务语义的边界将底层异常转换一次，避免每层重复包装。

### 8.2 错误码

- 【必须】复用现有 `ErrorCode`，同一失败语义不能创建多个错误码。
- 【必须】错误码名称和消息准确描述调用方可理解的失败，不暴露内部组件。
- 【必须】新增错误码时同步更新实际接口文档和相应行为测试。
- 【应当】错误消息告诉调用方哪里不符合契约，不包含排查过程和内部异常文本。

### 8.3 日志

- 【必须】使用日志框架占位符，不使用字符串拼接构造日志。
- 【必须】异常只在能够处理或最终负责记录的边界记录一次，避免同一异常重复打印。
- 【必须】日志不能包含密码、密码哈希、验证码、JWT、Refresh Token、密钥、完整手机号、完整邮箱或身份证件。
- 【必须】生产代码不使用 `System.out`、`System.err` 或 `printStackTrace`。
- 【应当】`ERROR` 表示需要处理的系统失败，`WARN` 表示可恢复但值得关注的异常状态，`INFO` 记录关键业务状态变化。
- 【应当】高频路径避免逐条输出大对象或完整请求体。

## 9. Spring Boot 分层规则

### 9.1 Controller

- 【必须】Controller 只负责 HTTP 路由、参数绑定与校验、认证上下文读取和响应转换。
- 【必须】请求参数使用 Bean Validation 表达格式约束，并在入口启用校验。
- 【必须】Controller 不直接访问 Mapper、Redis 或外部服务，不实现业务事务。
- 【必须】遵循项目统一的 `Result`、分页和异常处理结构。
- 【应当】Controller 方法短而清楚，将业务判断交给 Service。

### 9.2 Service

- 【必须】Service 负责业务规则、状态变化和事务边界。
- 【必须】明确各项规则的责任层级：数据库约束保证最终唯一性，Service 校验业务状态和资源归属，Spring Security 负责统一认证和接口访问权限；不重复实现同一规则，也不把不同职责的检查合并删除。
- 【必须】业务方法返回领域结果或 VO 所需数据，不返回 HTTP 对象。
- 【应当】同一业务用例在一个服务入口内完成，避免 Controller 串联多个服务拼装事务。

### 9.3 依赖注入与配置

- 【必须】使用构造器注入，不使用字段注入。
- 【必须】配置项通过类型安全的配置对象读取，不在业务代码散落读取环境变量。
- 【必须】密钥、密码和环境差异配置不能硬编码进生产源码。
- 【应当】只有多个 Bean 无法由类型区分时使用 `@Qualifier`。
- 【应当】配置默认值只服务本地开发，并清楚记录部署环境的覆盖方式。

### 9.4 事务

- 【必须】事务边界放在 Service 的公开业务方法上。
- 【必须】了解 Spring 代理边界；不能依赖同类内部调用触发 `@Transactional`。
- 【必须】事务内的数据库写入必须形成一个清楚的一致性单元。
- 【必须】按业务契约检查更新或删除的影响行数：预期修改指定记录时验证是否命中，幂等删除或重复提交按约定判断成功。结合驱动返回“匹配行数”或“实际变更行数”的语义解释零行结果，不能统一认定为成功或失败。
- 【应当】事务尽量短。远程调用、文件处理和长时间计算不放在数据库事务中，除非业务一致性明确要求。
- 【应当】只读查询在确有收益且项目已有约定时使用只读事务，不机械添加。

## 10. MyBatis 与 SQL

- 【必须】Mapper 接口、XML statement、参数名、返回类型和 `resultMap` 保持一致。
- 【必须】SQL 参数使用 `#{}` 绑定，不把外部输入通过 `${}` 拼入 SQL。
- 【必须】动态表名、列名和排序字段必须来自服务端固定白名单。
- 【必须】查询明确列名，不使用 `SELECT *`。
- 【必须】复杂映射使用显式 `resultMap`，尤其是下划线字段、布尔字段和多表同名列。
- 【必须】多表查询使用清楚的表别名，并为同名返回列声明不冲突的列别名。
- 【必须】批量写入限制单次数量，避免无上限 SQL 和参数集合。
- 【必须】修改 Mapper 时同步检查 XML、Service 调用和测试。
- 【应当】简单 SQL 保持直接，不为复用少量片段制造难以追踪的动态 SQL。
- 【应当】只有查询结构确实复杂且重复时才抽取 `<sql>` 片段。

## 11. MySQL 设计规则

### 11.1 表与字段

- 【必须】表名、字段名使用小写 `snake_case`，不使用数据库保留字。
- 【必须】表名使用单数业务实体名，并与 Java Entity 语义一致。
- 【必须】每张业务表定义明确主键；是否自增按项目现有主键策略执行。
- 【必须】业务唯一性由唯一索引保证，不能只依赖应用层“先查询再插入”。
- 【必须】小数使用 `DECIMAL`，金额精度和单位必须明确。
- 【必须】字符串长度、是否可空和默认值根据真实数据约束定义，不统一使用超大 `VARCHAR`。
- 【必须】布尔列使用项目统一的 `is_xxx` 命名和数值约定，并在 Java 层映射为不带 `is` 前缀的属性。
- 【必须】字段含义、枚举取值或单位无法从名称看出时添加数据库注释。
- 【应当】保留项目统一的创建时间和更新时间字段。
- 【应当】物理删除或逻辑删除按当前业务的追溯、唯一性和数据保留要求选择，不机械套用一种方式。

### 11.2 索引与查询

- 【必须】索引来自真实查询条件、关联、排序和唯一性约束，不为每个字段建立索引。
- 【必须】组合索引顺序依据等值条件、范围条件、排序和区分度设计，并用实际 SQL 验证。
- 【必须】关联列的数据类型、长度和字符集保持一致。
- 【必须】分页参数有上限；大偏移分页出现性能问题时使用游标或基于索引的翻页。
- 【必须】不要对需要索引加速的查询使用左模糊匹配或包裹索引列的无必要函数。
- 【应当】修改核心查询或索引时使用 `EXPLAIN` 检查执行计划，并结合实际数据量判断。
- 【应当】避免超过当前需求的分库分表、读写分离和冗余字段设计。

### 11.3 SQL 语义

- 【必须】统计行数使用 `COUNT(*)`。
- 【必须】理解 `NULL` 语义；聚合函数可能返回 `NULL` 时在 SQL 或 Java 边界明确处理。
- 【必须】更新和删除必须有准确条件。批量影响数据前验证作用范围。
- 【必须】不能用外键、触发器、存储过程或应用锁叠加实现同一规则，除非项目明确采用。
- 【应当】一个查询完成一个清楚目标。不要为减少 SQL 次数制造难以维护的大型多表查询。

## 12. 安全规则

- 【必须】所有外部输入都按类型、长度、格式、范围和数量验证。
- 【必须】认证和授权使用 Spring Security 的统一链路，不在 Controller 中手写替代鉴权。
- 【必须】密码只使用项目配置的 `PasswordEncoder` 处理，不自行实现哈希或加密。
- 【必须】Access Token 与 Refresh Token 按 `tokenType` 和使用场景严格隔离。
- 【必须】SQL、命令、模板、HTML 和 URL 按目标上下文使用参数绑定、转义或白名单，禁止直接拼接不可信输入。
- 【必须】文件上传校验大小、类型、文件名和存储位置；不能信任客户端声明的 MIME 类型。
- 【必须】外部重定向目标使用固定白名单。
- 【必须】验证码、短信、邮件、登录、重置密码等高风险入口实施当前需求规定的频率、次数和一次性消费限制。
- 【必须】日志、接口响应、异常和测试输出都不能泄露凭据与敏感信息。
- 【必须】远程调用设置明确的连接和读取超时。
- 【应当】按最小权限开放接口和数据，只返回调用方需要的字段。
- 【应当】安全机制解决真实威胁模型，不重复叠加用途相同的校验、Token 或锁。

## 13. 依赖与配置

- 【必须】新增依赖前确认 JDK、Spring Boot 或已有依赖无法合理完成需求。
- 【必须】依赖版本与 Spring Boot BOM 和项目现有版本策略一致，不在多个模块重复声明冲突版本。
- 【必须】不能使用已废弃 API 或已知不兼容当前 JDK/Spring Boot 的库。
- 【必须】正式环境不依赖第三方 `SNAPSHOT` 版本。
- 【必须】升级依赖时检查传递依赖、编译、测试和运行时行为。
- 【应当】优先选择维护活跃、用途明确、依赖范围小的库。
- 【应当】不引入功能重叠的工具包，不创建大而全的 `Utils` 类。

## 14. 测试规则

- 【必须】测试验证可观察行为、业务边界和真实失败路径，不照抄实现步骤。
- 【必须】修复缺陷时添加能在修复前失败、修复后通过的回归测试，除非已有测试已准确覆盖。
- 【必须】认证、权限、事务、SQL 映射、Redis 原子操作等框架行为，使用能够覆盖真实集成边界的测试。
- 【必须】Mock 只隔离当前测试范围之外的依赖，不能用 Mock 证明数据库、Redis、Security Filter 或序列化真实可用。
- 【必须】跳过的测试记录为“未验证”，不能汇报为通过。
- 【必须】测试数据不能依赖执行顺序、共享残留状态或生产凭据。
- 【必须】本次改动明确列出的需求、关键业务分支和已识别失败场景，全部有对应验证及结果断言；发现遗漏时补充场景，不能缩减清单制造达标。
- 【必须】需要采集覆盖率时，使用工具记录行覆盖率与分支覆盖率，明确统计范围和未覆盖的关键代码。没有采集结果时记录为“未采集”，不能估算或宣称达到 100%。
- 【必须】不把代码行覆盖率或分支覆盖率 100% 作为统一硬性门槛；覆盖率数字不能代替业务、并发或真实集成验证。
- 【应当】优先覆盖高风险分支、状态变化、边界值和错误路径，不追求无意义覆盖率数字。
- 【应当】可逆的纯文档或低风险格式修改不新增测试。
- 【必须】后端构建与测试使用项目 Maven Wrapper 和 JDK 25；最终需要执行的检查以[后端质量门禁](quality-gates.md)为准。

## 15. 文档与交付

- 【必须】`docs/api.md` 只记录已经实现的接口；计划中的接口放在方案文档中。
- 【必须】接口、配置、数据库结构或运行方式发生变化时，更新对应事实文档。
- 【必须】文档描述最终行为，不记录无关的尝试过程和已放弃方案。
- 【必须】完成修改后检查 `git diff` 和 `git status`，确认没有无关文件、临时文件、生成物或凭据。
- 【必须】运行与修改风险相匹配的测试和构建，并准确报告通过、失败、跳过和未执行项。
- 【必须】后端代码修改按[后端质量门禁](quality-gates.md)完成规范检查、代码 Review 和测试验收；存在未解决的问题或缺少必需验证时，交付状态为“未通过门禁”。
- 【必须】不能用编译通过代替业务验证，也不能用单元测试通过代替真实数据库或 Redis 验证。
- 【必须】提交前执行 `git diff --check`，处理空白错误和冲突标记。
- 【必须】除非用户明确要求，不提交、不推送、不删除用户数据或清理用户已有工作。

## 16. AI 完成任务前检查

AI 在交付 Java 修改前逐项确认：

- [ ] 修改直接对应当前需求，没有附带功能和假想兼容。
- [ ] 已检查调用方、接口、数据库映射、配置和相关测试。
- [ ] Controller、Service、Mapper、DTO、VO、Entity 职责清楚。
- [ ] 代码流程清晰、容易修改和排障，注释说明关键约束，没有无需求的教学内容。
- [ ] 输入格式在各个不可信入口校验，内部未重复同一校验，业务状态、资源归属、权限和数据库约束完整保留。
- [ ] 没有泄露密码、Token、验证码、密钥和完整敏感信息。
- [ ] SQL 使用参数绑定，唯一性和并发约束由正确层级保证。
- [ ] 异常没有被吞掉，错误响应没有暴露内部细节。
- [ ] 没有无需求的抽象、依赖、锁、重试、缓存或兼容层。
- [ ] 数据库结构变更使用新的、不可变的 Flyway 版本迁移；没有修改已发布的迁移文件；相关数据库文档和集成测试已同步。
- [ ] 测试覆盖本次修改的关键行为，而不是实现细节。
- [ ] 已执行适当验证，并区分通过、跳过与未验证。
- [ ] 已按后端质量门禁完成对应检查，测试场景与覆盖率结果可核对，没有把构建成功等同于全部验收通过。
- [ ] diff 中没有无关改动、临时文件或覆盖用户已有修改。
